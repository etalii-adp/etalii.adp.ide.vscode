# What this plug-in supports of DISL, DESL and FBL

The plug-in reads a tool type from its definition: a DISL specification for a diagram or a DESL specification for a designer, with its FBL bindings and its companion document, copied unchanged into `definitions/<tool>/`. One interpreter (`src/core/disl/`, with what DESL adds in `src/core/desl/`), one scene (`src/core/scene/`), one table view (`src/core/tool/tableView.ts`) and one function (`toolTypeFrom` in `src/core/tool/`) turn any such folder into a tool type. This page says what they read of a definition and what they do not, which behaviours this host had to choose because a definition leaves them unstated, where a tool type here differs from its definition, and which differences are raised with `etalii.adp` and settled nowhere here.

Read it before copying a definition, to know whether it will work in this host, and when writing one, to know what this host does with a construct. A definition that asks for more than this page lists still opens: what is not supported is read as the nearest thing that is, and reported as a finding in the Problems panel.

Two other records stand beside this one and are not repeated here. [docs/parity.md](parity.md) holds the differences from the standalone modules, and [docs/fbl.md](fbl.md) holds what the FBL library implements.

## Versions

| Language | Version read | What happens with a newer minor version |
| --- | --- | --- |
| DISL | 0.4 | The specification opens, with one finding (`disl.specification`, warning) that says it is newer than the DISL this host reads |
| DESL | 0.1 | The specification opens, with one finding (`desl.specification`, warning) that says it is newer than the DESL this host reads |
| FBL | 0.1 to 0.6 | A binding of 0.7 or newer loads with a warning. See [docs/fbl.md](fbl.md) |

A specification or a binding of another major version does not load, and its folder is no tool type.

## Conformance class and features

The list is the one of [`src/core/disl/support.ts`](../src/core/disl/support.ts): a feature is added there by the change that builds it, and to this table with it. A test holds the two together. A specification whose `language.requires` names another feature, or a higher conformance class, opens with one finding for each (`disl.unsupported-feature`, `disl.unsupported-conformance`, both warnings).

The conformance class is `standard`.

| Feature | What is built |
| --- | --- |
| `axis.yearMonth` | A time axis whose values are a year and a month, counted in months, with a unit of a month or coarser that may be bound to an attribute of the diagram |
| `ruler.adaptive` | A ruler whose levels are shown by the room their labels have on screen (`minSpacingPx`, `minZoom`, `maxZoom`, `step`), never finer than `minUnit` |
| `snap.byGesture` | Snapping rules per gesture, read with the coordinate system and the node notation |
| `anchor.part` | An edge end on a part of a composite shape, on a side of it and a fraction along that side |
| `anchor.sides` | An edge end at the middle of one of the sides of its node that the notation names, the one nearest the other end |
| `canvas.filters` | The filters of `notation.canvas.filters` with the controls `chips`, `switch`, `select` and `search`, the effects `hide` and `dim`, and matching any or all |
| `viewpoint.variants` | A viewpoint that varies another, offered as its `toggle` |
| `placement.bound` | A node placed by its attributes on both axes, with `x2`, `y2`, `width`, `height`, `offset` and an anchor |
| `shape.custom` | A shape declared as path segments with parameters and handles |
| `shape.composite` | A shape made of parts, each with its own shape, box, style, condition and tooltip |
| `edge.bezier` | An edge drawn as a cubic curve, with `startDirection`, `endDirection`, `reach` and `maxReach` |
| `label.parse` | A label whose edited text is parsed and written by the specification's own rule |
| `persistence.fbl` | A document read and written through an FBL binding |
| `view.viewer` | Viewer state that is a fold: `persistence.view.viewer` with `collapsed`, seeded by `view.initial`, read as `self.view.collapsed`, changed by a `view` action, kept per open editor and never written |

DISL 0.4 names no feature identifier for what it adds (its Appendix B.8 ends at 0.3, see issue [159](https://github.com/etalii-adp/etalii.adp/issues/159)), so a specification cannot require those constructs by name and this table cannot list them. What is read of them is in the next section: grouped compartments with an item order and item links, a kept filter, `pin`, `unpin` and `unpinAll`, the `open` action, the `force` layout in tiers, `paths` on a `uri` attribute and `persistence.view.bind`.

A tidy tree places every drawn node by containment, a node whose parent is not drawn as a root. With `rows.stored: "y"` a row is drawn at the first height kept for any of its nodes. A drag in it is the tree's: with `drag.across: "reorder"`, dropped past the middle of a sibling the node takes that sibling's place in the model; with `drag.down: "row"`, the height it is dropped at is kept for every node of its row and beneath it; both as one edit. A drop from the toolbox keeps no place. A layout named `plugin:<id>` is run by the layout plugin of that id: it is given what is drawn, the notation's sizes, and the configuration's `spacing` and `options`, and it places the nodes and may size them. Where the optional plugin is not carried, the algorithm its `fallback.layout` names stands in. With `trigger: "always"` or `"onChange"`, the `default` layout is the layout of every viewpoint that names none, and it is run whenever a view is made. `respect: "pinned"`: a pinned node is where the document keeps it and the layout places the others around it; a drag of a node the layout placed, and a drop from the toolbox, pin it, except in a tidy tree | A `tidyTree` with another `direction` than `down` is drawn downwards, and reported. Another algorithm is not run: the nodes it should place stand at the origin, and a finding says so. The triggers `onCreate` and `onLoadIfMissing` are read as `manual`. `respect: "all"` is read as `none`. `incremental` and `animate` are not read: a node is drawn at its new place at once |
| `constraints` | Invariants and gesture constraints with `scope`, `forEach`, `when`, `rule`, `severity`, `message`, `target`, `location`, `subject`, `attribute`, `timing`, `enforcement`, `enabled` and `group`; `defaults`, `order`, `blockSaveOn`, `builtIn` | A rule `over` a view is left out and reported. Quick fixes and suppressions are not read |
| `behavior` | `messages`, `reasons`, `editGate`, hooks, operations, `deletion`, and the actions `set`, `unset`, `create` (with `after` and `before`), `connect`, `delete`, `reorder`, `reparent`, `retype`, `let`, `if`, `forEach`, `layout` (the `rows` algorithm), `abort`, `call`, `select`, `reveal`, `highlight`, `editLabel`, `openForm`, `notify`, `open`, and `view` for `collapsed`, `pinned`, `groups` and the kept filters among `filters`. `open` takes an `http` or `https` address and a path, and refuses any other link with a sentence that names it (DISL 9.4). A default that is computed is worked out when an element is created. An operation that names a `plugin` is run by the action plugin of that name. Any other standard entry (`duplicate`, `openForm`, `connect`, `create-connected`) is shown, and asking for it is refused with a sentence. An entry's `submenu` is not read |
| `forms` | The inspector form of a type, or one made from its attributes: sections, fields, computed items, `visible`, `readOnly` with its reasons, `validate`, `parse`, `display`, options. The other kinds of `view.store` (`bounds` among them: a registration keeps a corner, not a size) are not read, and `view.revealExpands` is read as true. | DESL: `surface` (7) | The kind `table`: `columns`, `rows`, `cells`, `views` and `valueTypes`, with the name checks of 10.1, step 4. | DESL: `operations` (8) | Every operation, with `for`, `params` and their defaults, `unavailable`, `confirm` with `count` and `threshold`, and the actions `set`, `unset`, `create` with `parent`, `slot`, `after` and `before`, `delete`, `reorder`, `let`, `if` and `forEach`. | DESL: the CEL environment (9) | `document` with `elements`, `elementsOfType` and `elementById`; an element's `parent`, `slot`, `children`, `childrenOfType`, `ancestors`, `ancestorsOfType`, `positionIn` and `label`; `uniqueName` and `isUnique`; `p`, `selection`, `count` and the names an action binds | Expressions are not type-checked or costed when a specification is read: one that cannot be parsed is a finding, and one that fails is handled as DESL 2.5 says |

## Plugins

A plugin is code for one tool type, kept under `src/core/plugins/<plugin>/` and registered by its id in [`src/core/plugins/index.ts`](../src/core/plugins/index.ts), which is the only place its id appears outside its own folder. A test holds this section to that registry: every plugin carried is a row here with its id, what it provides, its folder and the definitions that name it.

| Plugin | Provides | Folder | Named by |
| --- | --- | --- | --- |
| `net.etalii.adp.freeplane.mm` | persistence | `src/core/plugins/freeplane-mm/` | Mind map |
| `net.etalii.adp.freeplane.mindmapLayout` | layout | `src/core/plugins/mindmap-layout/` | Mind map |
| `net.etalii.adp.etalii.abmMarkdown` | persistence | `src/core/plugins/abm-markdown/` | Agent Behavior Modelling |
| `net.etalii.adp.etalii.abmArrange` | action | `src/core/plugins/abm-arrange/`, which answers with the registration without its `layout:` block | Agent Behavior Modelling |
| `net.etalii.adp.ide.projectLinkPicker` | action | `src/core/plugins/project-link-picker/`, which answers with the outcome `pickPath`; the dialog is the platform's, shown by `src/extension/projectLinkPicker.ts` | Mind map |

What happens for a plugin that a definition or a binding names and this host does not carry:

- A plugin declared `required: true`, and the plugin a binding names as its `reader`, makes every document of the tool type read-only. The document opens with what can be read without the plugin, the finding `std.pluginMissing` names the plugin with FBL's sentence, the same sentence is the notice over the canvas, nothing that edits is offered, and every request is refused with it.
- A plugin declared `required: false` gives no finding. A layout it provides is replaced by the algorithm its `fallback.layout` names. An operation it provides changes nothing.

## Code for one tool type

Nothing under `src/core/disl/`, `src/core/desl/`, `src/core/scene/` and `src/core/tool/` names a tool type, which a test holds by reading those folders for every name the copied definitions declare. Code for one tool type exists in these places outside a plugin.

| Where | What | Why |
| --- | --- | --- |
| `src/core/plugins/knowledge-views/`, registered by the tool type's origin in `src/core/plugins/index.ts` and reached through the plugin registry (`views`) | What a view of the Knowledge designer shows: which columns and how, the rows its filter keeps in the order its sorts give, its groups, the line under a column, and the colour of each of the ten option colours for a light and a dark theme | DESL names the types that store a view's settings by their role and not what an attribute of them means (DESL 7.4), and `knowledge.md` says the view logic is each host's to implement. The definition names no plugin for it, so it is no row of the table above. A designer without such code shows every column and every row in the document's order. Issue [162](https://github.com/etalii-adp/etalii.adp/issues/162) asks DESL to name these attributes |

## What this host decides

Behaviour a definition leaves unstated and this host had to choose. A rule names no tool type.

| Behaviour | Rule followed | Where |
| --- | --- | --- |
| The mode of a theme | A definition's theme gives its tokens for `light` and `dark`. Light and high contrast light themes read `light`; dark and high contrast themes read `dark`. In both high contrast kinds outlines take the editor's contrast border and text its foreground, so nothing depends on a fill alone. A token with no value in the mode takes the editor's own colour for that role | The scene carries every token with both values (`Scene.tokens`); the webview chooses |
| Where an action at a point lands | An operation that reads `position` runs at the point the request names. A request without one, as from the Command Palette, takes the middle of what the canvas shows. In a viewpoint that places by layout the point is read back onto the axes of the viewpoint it varies, as a drop is | `edit` in `src/core/tool/toolTypeFrom.ts` |
| A tool dropped in a viewpoint that places by layout | Between two placed elements the coordinate runs evenly from the one's own place to the other's, beyond the first and the last it runs at the scale of the base axis, and with nothing placed it is the point itself | `baseCoordinate` in `src/core/disl/behavior.ts` |
| An edge end that names a part or a side its node does not have | The end is drawn at the first place it could name: the first part and the first side its attributes allow, halfway along, and marked `fallback` in the scene.
